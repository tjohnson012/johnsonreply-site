Field notes

A major upgrade broke 12 of my 75 tests. None of them were bugs.

Then "it passed three times in a row" turned out not to be proof. Here's everything that broke when I upgraded a Playwright suite across a major version of Ghost, and why each one broke.

Tyler Johnson, SDET · November 2026 · 8 min read

I keep a public Playwright suite for Ghost, the open-source publishing platform. It's a sample of the work I do for clients: 20 tests run in Chrome, Safari, Firefox and on an iPhone, which makes 75 runs (counting a one-time login) on every push. It covers member signup by real emailed magic link, members-only posts, the admin editor, and basic site health.

This week I upgraded it from Ghost 5.130 to Ghost 6.78. That's a major version, so the admin editor was rebuilt and the sign-in API changed. This is the exact situation that makes teams nervous about their E2E suite, so I wrote down everything.

Round 1: twelve failures, five causes

Twelve red tests looks like a disaster. It was five problems, each showing up in several browsers. The job is to put every failure in one of two buckets: the product broke, or the product changed on purpose and the test is out of date. All five were the second kind.

1. The sign-in API grew an anti-spam token

To sign in a test member quickly, the suite calls Ghost's send-magic-link endpoint directly. Ghost 6 now requires an integrity token, and without it the endpoint returns 400. Signing up through the real popup kept working, because Ghost's own popup fetches the token itself. So the shortcut was out of date, not the product.

// fetch the token first, the way Ghost's own popup does
const tokenRes = await api.get('/members/api/integrity-token/');
const integrityToken = tokenRes.ok() ? await tokenRes.text() : undefined;
const res = await api.post('/members/api/send-magic-link/', {
  data: { email, emailType: 'signup', integrityToken },
});
expect(res.status(), await res.text()).toBe(201);

That last line matters. One test called this endpoint without checking the response, so it failed later with "no email arrived" when the real error was a 400 three steps earlier. Assert where things happen, not where they're noticed.

2. A test hook disappeared in the editor rebuild

The old selector was [data-test-editor-title-input]. Ghost 6 rebuilt the editor and that attribute is gone. I didn't swap it for the new internal attribute; I switched to what a user sees: getByRole('textbox', { name: 'Post title' }). The accessible name survives redesigns. Internal test hooks don't.

3. A hidden copy of the editor

Clicking into the post body hung. Ghost 6 keeps a second, hidden editor instance in the page, and the old selector matched the hidden one first. Fix: target the visible editor only. This one is worth remembering. "Element exists" and "element a user can interact with" are different things.

4. The Publish button "covered" by the page. Not a bug.

This is the one I was most tempted to report as a bug. Playwright said the Publish button was visible and enabled, but another element was "intercepting pointer events." A real mouse click at those coordinates did nothing.

The cause: Ghost 6 fades the header out while you type (opacity 0, clicks pass straight through), and brings it back when the mouse moves. A person always moves the mouse toward the Publish button. A test that teleports the cursor doesn't. I confirmed it by checking what's under the pointer before and after moving the mouse.

// Move the mouse like a person would before reaching for Publish.
await page.mouse.move(200, 200, { steps: 5 });
await page.getByRole('button', { name: 'Publish', exact: true }).click();

Had I filed that as a bug, I'd have spent a client's time on intended behavior. Telling "changed on purpose" from "broke" quickly is most of the value in maintaining a suite.

5. The confirmation screen changed

Ghost 5 showed "Boom! It's out there" after publishing. Ghost 6 closes the dialog and sends you to the posts list. Sometimes it also shows a celebration popup, depending on the state of the site. A test can't depend on "sometimes," so done now means "you're on the posts list." I also checked through the API that the post really is published.

After those fixes, the suite passed three times in a row. Normally that's where you'd call it done.

Round 2: "passed three times" isn't proof

CI then failed 1 of 75. One intermittent failure in CI usually means there are more you haven't seen yet. So instead of re-running until it went green, I ran the affected tests 8 to 20 times each, in parallel, and gave every failure a root cause before touching it.

The first row is the one I'd point to. The flakiest failure was my mistake: an assertion that passed for the wrong reason. Most flaky tests aren't caused by an unreliable product. They're caused by a test asserting something slightly different from what the author meant.

Every fix was proven the same way: the affected tests run 8 to 20 times each, in parallel, with zero failures. Then the full suite went through four clean CI runs. A side effect: with the CDN out of the loop, a full local run dropped from 1.9 minutes to about 30 seconds. CI stayed around 1.5 to 2 minutes, since each CI run starts with an empty cache.

What I'd tell a team about to upgrade

  • Sort every failure before fixing any. "Broke" or "changed on purpose." The second kind is most of them, and treating them as bugs wastes everyone's week.
  • Select elements the way users find them. By role and accessible name, not internal test attributes. It's the cheapest upgrade insurance there is.
  • Assert outcomes, not in-between states. "The button changed" isn't "the post published." Most of my flakiness came from this.
  • Never use retries to fix flakiness. Run the test 20 times in parallel instead. If it fails once, there's a cause, and it's usually a race in the test.
  • Make test data unique under parallelism. Timestamps aren't unique enough.
  • Don't let your suite depend on someone else's CDN. Your app can be fast and your tests still time out.
